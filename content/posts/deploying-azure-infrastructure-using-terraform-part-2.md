In [Part 1](https://chinmaymjog.github.io/posts/architecture-of-a-shared-hosting-platform-on-azure-part-1/)
I walked through the Hub-Spoke architecture behind the shared hosting
platform. This post is about turning that design into Terraform: how the
code is split, how the pieces find each other, and the order I deploy
them in.

The full source is in
[azure-vm-hosting-solution](https://github.com/chinmaymjog/azure-vm-hosting-solution).

## Two stacks, not one

The Terraform is split into two independent root modules, each with its
own state file:

- **`shared-hub`** - the management side: the Hub VNet, a Key Vault, the
  backup storage (Azure Files Premium NFS), a shared SSH key, and the
  Jumpbox VM that later runs Jenkins and Ansible.
- **`platform`** - the hosting side: the Spoke VNet, Azure Front Door
  with a WAF policy, the public Load Balancer, the web VM fleet, MySQL
  Flexible Server, and the website storage (also Azure Files Premium
  NFS).

I split them because they change at completely different speeds. The
Hub is something I deploy once and rarely touch. The Platform is what I
re-apply when I scale the VM count or change a database SKU, and I don't
want a plan on the Platform to ever have an opinion about the Key Vault.

## How the stacks find each other

The Platform needs things the Hub created: the Key Vault holding the
MySQL password, the shared SSH public key, and the backup storage
account. Instead of passing IDs around by hand or reading remote state,
the Hub tags what it creates (`Role = SharedVault`, `SharedSSH`,
`SharedBackup`) and the Platform looks those resources up by tag:

```hcl
data "azurerm_resources" "hub_vault" {
  resource_group_name = "rg-${var.project_name}-hub"
  type                = "Microsoft.KeyVault/vaults"

  required_tags = {
    Role = "SharedVault"
  }
}
```

Both stacks derive resource group and VNet names from the same
`project_name`, so that one variable is the only thing tying them
together. The Platform also creates both halves of the VNet peering -
including the Hub-to-Spoke side, inside the Hub's resource group - so
deploying a Spoke is a single `apply`.

## No secrets in `.env` for Terraform

An earlier version of this setup exported a service principal's
`ARM_CLIENT_SECRET` from a `.env` file. I no longer do that. Terraform
authenticates through the Azure CLI (`az login`), and the only things
the repo's `.env` holds are non-secret names: the project prefix and the
location of the remote state.

The secrets that do exist are generated by Terraform and go straight into
the Key Vault: a random MySQL admin password and a 4096-bit RSA key
pair. The Platform reads the password from the vault when it creates the
database, and I download the private key from the vault when I need to
SSH in. Nothing is stored on disk in the repo.

## Configuration

Everything you'd tune lives in
`infra/terraform/platform/environments/main.tfvars`. The defaults are
deliberately small so a first deploy doesn't burn money:

```hcl
location             = "West Europe"
vm_count             = 2
vm_size              = "Standard_B1s"
vm_os_disk_size_gb   = 30
vm_data_disk_size_gb = 10
website_storage_gb   = 100              # Premium file shares start at 100 GB
mysql_sku            = "B_Standard_B1ms"
mysql_storage_gb     = 20
vnet_address_space   = ["10.0.0.0/16"]  # Spoke
hub_address_space    = ["10.10.0.0/16"] # Hub
```

The web VMs are spread over an availability set rather than pinned to an
Availability Zone, so there is no zone variable to keep in sync with the
storage. Scaling the fleet means changing `vm_count` and re-applying.

One thing that is easy to miss is `my_ip`. It controls where the
Jumpbox accepts SSH from. If you leave it unset, Terraform looks up the
public IP of the machine running the apply and uses that. If you set it,
wildcards like `*` and `0.0.0.0/0` are rejected by a validation block,
so you can't accidentally open SSH to the world.

## What is public and what isn't

It is worth being precise here, because the Terraform makes the answer
less tidy than "only Front Door is public":

- **Azure Front Door** is the intended entry point.
- **The Load Balancer has a public IP.** Front Door's origin is that IP.
  The compute subnet's NSG only allows ports 80/443 from the
  `AzureFrontDoor.Backend` service tag (plus the IP of whoever ran
  Terraform, for testing).
- **The Jumpbox has a public IP** too, with SSH restricted to `my_ip`,
  key-only login and Fail2Ban on top.
- **MySQL** is private, in a delegated subnet with a private DNS zone
  linked to both VNets.
- **Storage accounts** use default-deny network rules, private
  endpoints and private DNS, so the NFS shares are only reachable from
  inside the VNets.
- **The Key Vault** is default-deny, with access limited to the Hub
  subnet and the Jumpbox's managed identity.

Also worth knowing: the WAF policy is created in `Detection` mode. It
logs but does not block. Switch it to `Prevention` once you've watched
the logs for false positives.

## Deploying

The Makefile wraps the steps so I don't have to remember backend flags.
Terraform 1.5 or newer and the Azure CLI are all you need.

![Mermaid Diagram](/images/deploying-azure-infrastructure-using-terraform-part-2/mermaid_977d41bcf2aa.png)

1. `make setup` picks a unique project prefix and writes the state
   settings to `.env`.
2. `make bootstrap` creates the resource group, storage account and
   blob container that hold remote state.
3. `make hub-init` and `make hub-deploy` build the Hub.
4. Download the generated SSH private key from Key Vault.
5. `make infra-init` and `make infra-deploy` build the Platform.
6. `make jenkins-sync` and `make jenkins-up` hand over to Ansible and
   Jenkins - the subject of Part 3.

The Hub has to come first, since the Platform looks up the Key Vault,
SSH key and backup storage by tag and will fail to plan if they aren't
there.
